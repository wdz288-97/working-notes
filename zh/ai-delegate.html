用好 AI，第 4 章

拆分、委派、复用

阅读约 7 分钟

会交代任务、会检查 AI 的成果以后，接下来要想的是：哪些步骤交出去，工作怎么在几个 AI 之间交接，一套做法什么时候值得做成可复用的。

本章要点

  • 中间不需要人做重要判断的步骤，交出去。要判断的地方，留人把关。
  • 每个 AI、工具或人，各做自己最擅长的那部分。审阅的人除了结论，还要拿到证据。
  • 先用最简单、能跑通的做法。下一步要看查到了什么才能定的时候，再加 Agent（智能体）。
  • 交接要带上目标、已经定下的事、证据、目前的进度，还有没解决的问题。
  • 步骤会重复，搭建和维护的投入也收得回来，才值得把这套方法做成可复用的。Agent 只给完成任务需要的权限。

中间不需要判断的步骤，交出去

先把任务拆成几步，然后每一步都问一句：从这一步到下一步，中间有没有重要的地方要人来判断？能用代码完成，或者能让 Agent 操作电脑完成，中间又不需要这种判断的步骤，就适合交出去。有的步骤一旦走错代价很大，有的要靠只有你才清楚的情况才能做对。这些留给自己，或者加一道审阅。

这类任务要是你没做过，不用一个人琢磨怎么拆。看看别人做同类任务时怎么用 AI，自己试一试，经验慢慢就攒起来了。交出去的任务，第 3 章讲的检查点照样适用。

我的做法

能用代码或电脑操控自动完成、中间不需要人做重要判断的步骤，可以交给 AI 做。碰到没做过的任务，我会先查查别人是怎么用 AI 做的，边做边攒经验。

每个帮手，做它最擅长的那部分

把 AI 当成合作者以后，同时用好几个就很自然了。有的擅长找资料，有的擅长处理软件项目的代码，有的擅长讲解。这样分工，得边用边验证：产品在变，谁最擅长什么也跟着变。我现在怎么选，写在“用好 AI”页面上，标了日期。

帮手也不一定是 AI。算术交给计算器，比交给另一个大语言模型靠谱。初稿就算大半是 AI 写的，最合适的审阅人也可能是一位专家。该问的是：任务需要哪一块，哪种搭配能在成本可接受的情况下做好这一块。能把结果做出来、又能讲清依据的最小团队，通常就是最合适的。

谁来审阅，除了初稿的结论，还要把任务和证据一起给他。审阅的人如果只看到一份打磨好的答案，往往会连它的假设一起接过去。

从简单的做起，步骤不固定时才加 Agent

帮手越多，要协调的事就越多。Anthropic 讲怎么搭 Agent 的指南建议：从最简单的方案做起，只有能让结果变好，才加复杂度。1它区分了两种做法：

  • 工作流按你事先设计好的固定步骤走。
  • Agent 根据查到的情况，自己决定下一步。路径事先没法知道的时候，它就派上用场了。

什么都还没自动化，你也可以先手动把有用的工作串起来。把一份认真写好的任务说明，从一个工具挪到另一个工具，这就已经是工作流了。还没弄懂的流程就拿去自动化，只会让错误重复得更快。

交接要带上目标、证据和进度

工作在几个 AI 或几个对话之间流转时，要有一个明确的牵头方，负责把结果汇总起来、检查一遍。再把足够的信息交给下一个帮手，让它不用猜就能接着做：

  • 最初的目标，和已经定下的事
  • 到目前为止收集到的证据，各自从哪来
  • 工作现在的进度，以及用得上的文件
  • 还没解决的问题

只交一份打磨好的结论，下一个帮手就容易在没人核实过的假设上接着搭。协调和最后的审阅，跟任务大小相称就行，两步就能做完的任务，用不着项目计划。

我的做法

我手上没有现成的、用来协调多个 Agent 的工作流，所以这种事做得不多。真要做的时候，我用一个专做交接的 Skill（Matt Pocock 写的就不错），把工作干净地交给另一个 Agent。更简单的办法有两种：让主 Agent 自己启动一个帮手（子 Agent），或者把同一项目里之前某个对话的名称或 ID 告诉 Agent。我估计后一种更费 Token，不过没实际测过。

想清楚什么值得做成可复用的

同一类任务反复出现时，你可以一直用提示词，也可以写个 Skill、写段脚本、搭个 Agent，或者几样组合着用。选哪种，看三个问题：哪些步骤会重复，哪里需要判断，搭建和维护的投入换来的好处值不值。

Skill 就是把指令和资源打包好，Agent 用得上的时候再加载，2所以适合那种会重复、但每次跑都还要判断的方法。脚本适合每次都一模一样的步骤。没测过的方法存成 Skill，方便是留下了，错误也一起留下了，所以先拿真实工作测一测（第 5 章）。

把项目整理好，Agent 才能做好工作

项目要是专门为 Agent 收拾过，它就干得更好。这跟新同事一样：交接资料准备得好，工作就做得好。我采用了五条实用的原则，当作灵活的参考，不当成死规矩：

  1. 改动要好懂，影响范围要可控。每个模块自成一体，输入、输出和约束都写清楚。结构只在有用的地方加。
  2. 给一份简短的地图，指向要紧的东西。指明相关的项目知识、定义、决策、搭建步骤和专业指引在哪，别堆成一个巨大的指令文件。3
  3. 重要的要求，要能检查。用测试和检查把关，失败提示要写明该改什么，搭建和验证的命令也要写下来。光写指令，保证不了 Agent 照做。4
  4. 给 Agent 能核实实际结果的工具。做视觉类的任务，或者要它实际执行操作时，给它浏览器或电脑操控（直接操作屏幕、鼠标和键盘），第 3 章讲过。5
  5. 保留真正起作用的人工审阅。包括分析里那两个固定的检查点：验证原始输出，审阅最终解读。

好的工程习惯对人有用，对 Agent 也有用，道理是一样的。教 Agent 这些习惯的工程类 Skill，我一般从热门、知名的来源里挑，再拿自己的工作测一测。

任务需要什么权限，就给 Agent 什么权限

建议可以先审一遍再用。操作就不一样了，它可能已经改了文件、发出了消息，或者泄露了信息。Agent 能做的事越多，越需要划清界限。

  • 权限跟任务相称。能在安全的副本上做，就用副本。发送、删除、付款这类后果大的步骤，审批权留在你手里。
  • 写下的指令不是锁。提示词里写一句“什么都别发”，从技术上拦不住有发送权限的 Agent。
  • 弄清数据去了哪里。Agent 在你自己电脑上跑，不代表数据就留在本机，模型服务或接入的工具可能在别的地方运行。6
  • 页面里的文字不是指令。网页或文档里，可能有专门冲着 Agent 写的话。Agent 读到了，这些话也不能当成你的指令。6

常见误区：图省事，权限全给

权限全给 Agent，确实不会老被打断，直到它按错误的理解动了手。任务需要什么就给什么。等 Agent 在这类任务上证明靠得住，再一步步放宽。

自测一下

你每个月都要导一次同样的数据，步骤每次完全一样。用哪种做法最合适？

写个脚本。步骤重复、不变，中间也不用判断，搭建的投入很快就能收回来。

你把工作交给第二个 AI，只给了写好的初稿。缺了什么？

缺了目标、已经定下的事、证据和它的出处、当前进度，还有没解决的问题。少了这些，第二个 AI 就会在没人核实过的假设上接着做。

你在提示词里告诉 Agent“别给任何人发邮件”，而它能访问你的邮箱。这样安全吗？

不安全。指令在技术上拦不住它。任务用不到邮件，就别给 Agent 邮箱权限。用得到，就让每次发送都先经过你批准。
